Design system

Everything on this site is built from one set of Sass design tokens. Components never use raw colors or pixel values, so a change to a token updates every page in both themes. This page documents those tokens, the component states and how to use them.

Principles

  • Accessible by default

    Every color pair meets WCAG 2.1 AA in both themes, every control has a visible focus state and a 44px touch target.

  • Native first

    Buttons are buttons, inputs have labels, groups use fieldsets. ARIA only fills gaps that HTML cannot.

  • One source of truth

    Tokens live in src/scss/tokens. Components reference tokens, never hard coded values.

  • State is never color alone

    Selected tabs get a bar, invalid inputs get a thicker border and text, completed steps get an icon and words.

Color

Sass maps in tokens/_colors.scss are turned into CSS custom properties for light and dark themes. The values and contrast ratios below are read from the page as it is right now, so switch the theme and they update. Text needs 4.5:1 and UI parts like borders and focus rings need 3:1.

Usage guidance

Do

  • Use one primary button per screen for the main action
  • Label every field above the input, with hints between the label and the input
  • Mark optional fields, not required ones
  • Write error messages that say how to fix the problem, like "Enter your claimant ID"
  • Group related radios and checkboxes in a fieldset with the question as the legend
  • Use <a> to go somewhere and <button> to do something

Don't

  • Use placeholder text as a label
  • Disable the submit button until a form is valid. People cannot find out what is wrong.
  • Show state with color alone
  • Remove focus outlines without a stronger replacement
  • Add ARIA roles to elements that already have the right native role
  • Use raw hex values or pixel spacing in component styles

Design system vs Bootstrap

Bootstrap is a component library. A design system is the set of decisions, tokens, components, rules and documentation that a team agrees to share. Bootstrap can sit inside a design system, but it is not one by itself.

How an enterprise design system differs from using Bootstrap on its own
TopicBootstrap on its ownEnterprise design system
PurposeGeneric, ready made components to build quicklyOne shared look, behavior and voice across every product an organization runs
Source of truthBootstrap's own variables and defaultsDesign tokens owned by the organization, shared by design (Figma) and code
AccessibilityA reasonable base, but teams still own contrast, labels, focus and error handlingAccessibility rules are built into every component and tested before release
Content and patternsNone. It provides widgets, not guidance.Patterns like "ask for a date" or "show errors", plus writing guidance for labels and messages
GovernanceEach team customizes it differentlyVersioned releases, contribution process, and a team that owns it
ExamplesBootstrap 5U.S. Web Design System (USWDS), GOV.UK Design System, Microsoft Fluent, IBM Carbon

In practice I have worked both ways: Bootstrap 5 on the DWD portal and React dashboards, and a shared component library with Telerik UI on the Holman vendor portal. This site follows the design system approach, closer to how USWDS and GOV.UK are built.
