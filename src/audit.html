Case study

Accessibility audit of a legacy benefit claim form

I built a form the way many older government portals were built, audited it against WCAG 2.1 AA and Section 508, then rebuilt it. This is the same process I follow on real projects, shown on a fictional page so the code can be public.

Method

Standard

WCAG 2.1 Level A and AA, which is also the technical standard behind Section 508.

Automated testing

  • axe DevTools in the browser
  • pa11y running axe and HTML_CodeSniffer in the build pipeline
  • Lighthouse accessibility audit

Manual testing

  • Keyboard only: Tab, Shift+Tab, Enter, Space and arrow keys through the whole form
  • NVDA with Chrome and Firefox: headings list, landmarks, form mode and error announcements
  • Browser zoom at 200% and a 320px wide viewport for reflow
  • Contrast checks on text, hints, borders and focus indicators

Severity

Critical
Blocks someone from finishing the task
Serious
Task is possible but very hard or error prone
Moderate
Causes confusion or extra effort

Findings

Each issue is logged against its WCAG success criterion so the fix can be verified. On small screens the table scrolls sideways inside its own box, which can also be scrolled with the arrow keys once it has focus.

Audit findings for the legacy weekly benefit claim form
# Issue WCAG 2.1 criterion Severity Found by Fix
1 Text inputs have only placeholder text, no labels. The placeholder disappears as soon as someone types. 1.3.1 Info and Relationships (A), 3.3.2 Labels or Instructions (A), 4.1.2 Name, Role, Value (A) Critical HTML_CodeSniffer. axe did not flag it because it accepts a placeholder as an accessible name. Visible <label for> on every field, hints linked with aria-describedby
2 Submit is a div with an onclick handler, and the menu items are spans. None of them can be reached with a keyboard. 2.1.1 Keyboard (A), 4.1.2 Name, Role, Value (A) Critical Manual keyboard test Native <button type="submit"> and real links in a <nav> landmark
3 Errors are shown only as a red border. Nothing says what is wrong, and screen readers announce nothing. 3.3.1 Error Identification (A), 1.4.1 Use of Color (A), 4.1.3 Status Messages (AA) Critical Manual, NVDA Error summary that receives focus, text errors tied to fields with aria-describedby, aria-invalid, and a thicker border so state is not color alone
4 Radio buttons have no labels, and the question is not tied to the group. 1.3.1 Info and Relationships (A), 4.1.2 Name, Role, Value (A) Serious axe and HTML_CodeSniffer flagged the missing labels. The missing grouping was found with NVDA. <fieldset> with the question as <legend>, and a <label> on each option
5 Headings are bold divs, so there is no heading structure to navigate by. 1.3.1 Info and Relationships (A) Serious Manual, NVDA headings list was empty One h1 and h2 section headings in a logical order
6 Required fields are marked only by a red left border, explained as "fields in red are required". 1.4.1 Use of Color (A), 3.3.2 Labels or Instructions (A) Serious Manual All fields required by default, with "(optional)" in the label of the ones that are not
7 Hint and footer text is light gray (#aaa and #999 on white, about 2.3:1 and 2.8:1). 1.4.3 Contrast Minimum (AA) Serious axe and HTML_CodeSniffer Muted text token at 7.6:1 in light theme and 8.8:1 in dark theme
8 Focus outline removed with outline: none, so keyboard users cannot see where they are. 2.4.7 Focus Visible (AA) Serious Manual keyboard test 3px focus ring from a token that meets 3:1 against both themes, using :focus-visible
9 Fixed 960px layout. At 320px or 400% zoom the page scrolls in two directions. 1.4.10 Reflow (AA) Serious Manual zoom and narrow viewport Fluid layout with CSS Grid and min(), single column under 64em
10 "Previous weeks" table uses bold cells instead of header cells. 1.3.1 Info and Relationships (A) Serious Manual, NVDA table navigation read no headers <th scope="col">, row headers with scope="row", and a caption
11 Page has no lang attribute, so screen readers may use the wrong voice and pronunciation. 3.1.1 Language of Page (A) Serious axe and HTML_CodeSniffer <html lang="en">
12 No skip link and no landmarks. 2.4.1 Bypass Blocks (A) Moderate axe Skip link plus header, nav, main and footer landmarks
13 Agency logo image has no alt text. 1.1.1 Non-text Content (A) Moderate axe and HTML_CodeSniffer Descriptive alt text
14 Page title is "Untitled". 2.4.2 Page Titled (A) Moderate Manual. Tools only check that a title exists. Title that names the page and the site
15 Help link says "click here" and goes nowhere. 2.4.4 Link Purpose (A) Moderate Manual, NVDA links list Link text that makes sense on its own
16 Personal fields do not say what they collect, so browsers cannot autofill them. 1.3.5 Identify Input Purpose (AA) Moderate Manual code review autocomplete="name", email and tel, plus the right input types

Retest results

Automated

0 errors from axe and HTML_CodeSniffer in both light and dark themes. This runs on every push, and the deploy fails if anything comes back.

Keyboard

Every control is reachable in a logical order with a visible focus ring. Playwright tests check the error summary focus and links back to each field.

Screen reader

With NVDA, headings and landmarks are listed, each radio group reads its question, and errors are read when focus moves to the summary.

What this shows

Automated tools found 6 of the 16 problems, and axe on its own caught none of the three critical ones. The missing labels were only flagged by HTML_CodeSniffer, and the fake button and silent errors needed a keyboard and a screen reader to find. That is why I treat a clean axe report as the starting point, not the finish line.

Most fixes were not ARIA. They were native HTML used properly: labels, fieldsets, buttons, headings and table headers. ARIA was only needed to tie errors and hints to their fields and to mark invalid inputs.

This audit used NVDA. JAWS is the other screen reader most people use at work, government offices included, and it needs a paid license, so it was not part of this round. JAWS and NVDA switch between reading and forms mode in different ways, and each decides for itself how much of a description or group label to read. So on JAWS I would retest the parts that rely on that first: the error summary taking focus, error text tied to fields with aria-describedby, and the radio groups and date fields inside a fieldset.
